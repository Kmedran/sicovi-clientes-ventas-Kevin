4. CODIGO DE BASE DE DATOS
La migracion versionada de la seccion 3 contiene el codigo completo (PHP + SQL de
restricciones, indices y triggers). No hay SQL manual complementario.
Resumen del esquema creado:

  suppliers
    id bigint PK | code varchar(30) UNIQUE, default 'PRV-' || lpad(secuencia,6,'0')
    name varchar(180) NOT NULL | tax_id varchar(30) NOT NULL | contact_name varchar(150) NULL
    phone varchar(30) NULL | email varchar(254) NULL | address text NULL | notes text NULL
    active boolean default true | created_at, updated_at timestamptz
    UNIQUE: NIT normalizado (sin espacios ni guiones, minusculas); NIT obligatorio
    CHECK: name/code no vacios; NIT no vacio tras normalizar; opcionales no vacios si existen
    Indices: name; (active, name)

  purchases
    id bigint PK | code varchar(30) UNIQUE, default 'COM-' || lpad(secuencia,6,'0')
    supplier_id FK suppliers (RESTRICT) | warehouse_id FK warehouses (RESTRICT)
    document_date date | supplier_reference varchar(60) NULL
    state varchar(20) default 'draft' CHECK IN (draft, confirmed, voided)
    version integer default 0 CHECK >= 0 (control de edicion concurrente del borrador)
    notes text NULL | total numeric(16,2) default 0 CHECK >= 0
    created_by FK users | confirmed_by FK users NULL | confirmed_at timestamptz NULL
    confirmation_idempotency_key varchar(80) NULL
    voided_by FK users NULL | voided_at timestamptz NULL | void_reason text NULL
    UNIQUE parcial (supplier_id, referencia normalizada) cuando existe; NO se libera al anular
    UNIQUE parcial (confirmed_by, confirmation_idempotency_key)
    CHECK de consistencia de estado: draft sin datos de confirmacion/anulacion;
          confirmed con responsable y fecha; voided con ambos y motivo no vacio
    Indices: (supplier_id, document_date); (state, document_date); document_date; created_by

  purchase_items
    id bigint PK | purchase_id FK (RESTRICT) | product_id FK (RESTRICT) | unit_id FK (RESTRICT)
    product_sku varchar(50) | product_name varchar(180)   (copia historica)
    quantity numeric(14,3) CHECK > 0 | unit_cost numeric(14,2) CHECK >= 0
    line_total numeric(16,2) CHECK line_total = round(quantity * unit_cost, 2)
    UNIQUE (purchase_id, product_id): una linea por producto
    Indice: product_id

  idempotency_records
    id bigint PK | user_id FK users | action varchar(60) | idempotency_key varchar(80)
    request_hash char(64) CHECK sha256 hexadecimal minuscula
    result_type varchar(60) NULL | result_id bigint NULL (ambos NULL o ambos informados)
    created_at timestamptz default now()
    UNIQUE (user_id, action, idempotency_key)

  Secuencias: supplier_code_seq, purchase_code_seq (MAXVALUE 999999, NO CYCLE).
  Los numeros pueden tener saltos (un INSERT fallido consume numero); es esperado (contexto 8.3).

  Triggers de defensa (RN-07, RN-14, estados):
    purchases_state_guard        : una anulada no cambia de estado; una confirmada no vuelve a
                                   borrador; el contenido comercial confirmado/anulado y los datos
                                   de anulacion no se modifican.
    purchases_no_delete_confirmed: no se eliminan compras confirmadas ni anuladas.
    purchase_items_draft_only    : las lineas solo se insertan/editan/borran con la compra en
                                   borrador (usa FOR SHARE para esperar una confirmacion en curso).

7. COMPATIBILIDAD, RIESGOS Y DATOS EXISTENTES
- Solo crea objetos nuevos: conserva todos los datos existentes; no exige backfill.
- No cambia seeders, permisos ni tablas de Manuel en este cambio.
- Usa COLLATE pg_catalog.pg_c_utf8 igual que la migracion 000002: requiere PostgreSQL 17
  (el que usa el proyecto). En PostgreSQL 16 o inferior la migracion falla al crear.
- Si alguien ya creo manualmente tablas con estos nombres, la migracion falla sin
  sobrescribir; resolver con el autor antes de continuar.
- Decisiones de diseno que el equipo debe confirmar (afectan a Kevin/Luis):
    a) idempotency_records la crea este cambio; Kevin/Luis la reutilizan.
    b) Estados en BD: draft / confirmed / voided (UI: Borrador / Confirmada / Anulada).  [ACORDADO]
    c) Descartar un borrador = borrar fisicamente lineas y encabezado solo en borrador,
       sin afectar stock y con auditoria; no existe estado discarded.               [ACORDADO]
    d) Una linea por producto; si se repite en captura, se consolida.               [ACORDADO]
    e) NIT de proveedor OBLIGATORIO, normalizado y unico.                           [ACORDADO]
    f) La referencia del comprobante (proveedor + referencia) sigue siendo unica
       aunque la compra se anule, para no duplicar historicos.                      [ACORDADO]
- Regla para el equipo: toda migracion que cree funciones o tipos de PostgreSQL debe poder
  repetirse tras migrate:fresh en sicovi_test, que elimina tablas pero no funciones. Usar
  CREATE OR REPLACE FUNCTION. (El SQL sustituye al codigo ya aplicado: en sicovi_local la
  migracion se aplico con CREATE FUNCTION; el cambio no altera el esquema resultante.)
- Nunca usar migrate:fresh, db:wipe ni TRUNCATE para actualizar.
